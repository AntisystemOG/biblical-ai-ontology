## 19:02-19:12 CDT — MagneMotionMonitor "Connected but No Data" Fix

**Problem:** Thad connected to the MagneMotion network. App connected fine but showed no pallet data or any other information. Older version (v27.3.x) worked fine on the same network.

**Root cause:** The 6 new diagnostic tags added 8/8-8/9 (msg_path_cmd_timeout_count, msg_service_path_cmd_timer.ACC/.PRE, previous_hlc_heartbeat, hlc_link_monitor_timer.ACC/.PRE) were mixed into the main scalar tag batch in poll(). If ANY of these tags doesn't exist on the PLC, pycomm3 can fail the entire batch read, causing _read() to return {} — all fields get defaults, app shows zero data with no error.

**Fix (v32.7.3):** Moved the 6 diagnostic tags to a separate best-effort _read() call (same pattern as T_PROP_POWER). If they fail, only the diagnostic features degrade (gracefully); core data — pallets, vehicles, paths, stations, cold start — works normally.

## 19:02-19:40 CDT — MagneMotionMonitor "Connected but No Data" Fix (updated)

**Problem:** Thad connected to the MagneMotion network. App connected fine but showed no pallet data or any other information. Older version (v31.3.2) worked fine on the same network.

**Actual root cause:** The 6 new diagnostic tag constants (PT_MSG_PATH_CMD_TIMEOUT, PT_MSG_PATH_CMD_TIMER_ACC, etc.) were added to system_data.py but **NOT imported into plc_reader.py**. When poll() tried to reference them, Python raised NameError. The poll loop had a bare xcept Exception: pass, so the error was silently swallowed — no snapshot was emitted, app showed zero data.

**Fix (v32.7.3):**
1. Imported the missing 6 diagnostic tag constants in plc_reader.py.
2. Kept them in a separate best-effort _read() batch so future missing tags can't kill core polling.
3. Replaced the silent xcept: pass in _poll_loop with error logging to the Event Log so future failures are visible immediately.
4. Added log_error() method to EventLogPanel.

## 20:38-20:47 CDT — App Crashing on Open; Found Real Bug

**Problem:** App now crashes seconds after opening, even without starting a recording. Faulthandler logs showed v32.7.4 crashes at plc_reader.py:169/172 in _read during Garbage-collecting.

**Root cause discovered:** The _read() chunking added in v32.7.4 was broken for single-tag reads. pycomm3.tag.Tag is a namedtuple subclass, so isinstance(r, (list, tuple)) was True for a single Tag. The code then called esults.extend(r), which iterated the Tag's 4 fields (tag name string, value, type string, error) instead of treating it as one result. The comprehension {r.tag: r.value ...} then failed on the string field. The xcept Exception: return {} silently swallowed this, so every single-tag read returned an empty dict.

**Impact:** All single-tag reads were broken:
- Propulsion power (T_PROP_POWER)
- Motor-fault per-path batches (the new split reads)
- Any future single-tag read

This likely caused the poll loop to behave erratically and may have contributed to the crashes.

**Fixes applied:**
1. Import Tag from pycomm3 and detect single-Tag results explicitly: isinstance(r, Tag).
2. Keep _BATCH = 12 chunking for multi-tag reads.
3. Added gc.collect() at the start of each _poll_loop iteration to clear garbage before pycomm3 runs.
4. Bumped version to v32.7.5.

- Live PLC source poll verified: 24 pallets, 24 vehicles, 12 motor faults
- 140 tests pass
- Not committed/pushed to MagneMotion repo
